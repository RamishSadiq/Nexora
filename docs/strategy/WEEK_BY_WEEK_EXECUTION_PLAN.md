## Capacity, sequencing and ownership

Two experienced full-stack developers, eight-hour days, five-day weeks, 80% delivery availability: **eight effective developer-days per week**. Each weekly allocation includes design, implementation, integration, review and testing. The two developers can divide backend/data and frontend/journey work, but review each other's boundaries; this does not imply autonomous agent delegation.

Product owner provides weekly scope/acceptance decisions and design-partner access. UX, security, finance/privacy reviewers and pilot customers must be available at the stated gates. Their external fees/labour and procurement lead times are not included in developer-day totals. Keep one approved scope, one source of business rules and one integrated release candidate per week.

The table names the work to **design → develop → integrate → test → complete** each week. “Complete” means demonstrable evidence meets the gate, not simply that the calendar week ended. If a dependency fails, use reserve time and move dependent work; never silently waive an acceptance criterion.

## Reserve: weeks 33–40 / up to 64 developer-days equivalent

Reserve is not permission to add features. It absorbs higher-than-expected migration, identity, provider, security and pilot work. If V1 passes at W32, unused reserve is not automatically spent.

## Concrete API-contract work before coding

The following proposed contracts are a design starting point, not currently implemented endpoints. Preserve existing `/api/v1/crm/records` consumers with compatibility adapters while introducing restricted portal and integration surfaces.

| Contract | Inputs and identity | Result/invariants |
| --- | --- | --- |
| `GET /api/v1/crm/records/{id}/overview` | Staff principal with CRM resource access; no caller-supplied tenant | Header/version, allowed actions and permitted section summaries; suppress unauthorised counts |
| `GET /api/v1/crm/records/{id}/timeline` | Existing route evolved additively; cursor/type/date filters | Stable ordered source event IDs, actor display, safe summary, related route; no duplicate events |
| `GET/PATCH /api/v1/portal/me/profile` | Contact derived from verified binding; version/If-Match; allowlisted fields | Updated profile/version; no staff-only fields; 409 for stale write |
| `GET /api/v1/portal/me/accounts` | Active principal/tenant grant | Only explicitly granted accounts and permitted actions; relationship flag alone insufficient |
| `POST /api/v1/portal/applications` | Form version, product, optional granted account, evidence IDs, terms version; idempotency key | Stable draft/application ID and quote version; validation before submit |
| `POST /api/v1/portal/applications/{id}/submit` | Owned/granted draft; current version and accepted quote/terms | Submitted state + outbox; same key/body replays result, key with different body conflicts |
| `POST /api/v1/membership/applications/{id}/decision` | Existing route; staff `membership.decide`; version and reason | Atomic decision; approved entitlement remains pending until configured conditions hold |
| `POST /api/v1/portal/payment-sessions` | Authorised payable intent ID, idempotency key; amount determined by server | Provider checkout URL or pending attempt; caller cannot set charge amount or settlement status |
| `POST /api/v1/integrations/payments/{connection}/webhook` | Provider signature/raw body; connection resolves tenant/account | Durable inbox receipt then 2xx; processing result tracked; invalid signature denied |
| `GET /api/v1/portal/invoices/{id}` | Resource policy: own payer or account invoice grant | Safe invoice/settlement state; no tenant-wide finance scope |
| `POST /api/v1/documents/uploads` | Caller resource grant, metadata, bounded size/type | Quarantined upload reference; usable only after scan and link validation |
| `GET /api/v1/public/content/{slug}` | Verified host/site; published-only query | Cacheable published version; 404 for draft/unknown site; no identity data |
| `POST /api/v1/content/pages/{id}/publish` | Publisher role; expected page version | Published pointer/outbox/audit; 409 stale version; no unscanned/private media |
| `POST /api/v1/portal/cases` | Bound requester and optional granted account; safe attachments | Case ID/status, private internal workspace separated from public replies |

Define request/response schemas and executable examples for each before implementation. Common errors: malformed fields 400; unauthenticated 401; denied 403 or non-disclosing 404 by policy; missing 404; stale/idempotency conflict 409; quota 429 with retry guidance. Correlation IDs must be available without exposing internal exceptions. Integration keys use separate authentication from browser cookies; public endpoints do not acquire staff privileges through route reuse.

## Weekly review and scope control

Every Friday demonstrate one actual user outcome with evidence of its negative path. Update the debt register, migration status, tests and remaining estimate. Record actual developer-days against the phase, failed assumptions and any external delay. A new feature request must replace equal effort or explicitly change the timeline; it must not displace Must security/data-integrity/recovery work.

At W4, W11, W15, W20 and W32, check customer value as well as technical correctness. If design partners do not need corporate representation, or cannot justify switching costs, change the product focus before expanding the suite. The first task after approval is P0/P1 baseline work, not another isolated CRM screen.
